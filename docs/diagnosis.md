# 首轮失败归因：适配代码、资源合同与模型能力

本诊断基于 `runs/sica-qwen-20261011` 的既有轨迹与模型请求离线审计，没有新增推理调用，也没有修改冻结版本或原始实验结果。机器可读证据位于 [offline_audit.json](../runs/sica-qwen-20261011/diagnosis/offline_audit.json)。

## 判断

**已确认适配与反馈问题，尚不能把失败主要归因为模型能力不足。** 五份提案都在读取阶段触发宿主限制，未尝试写入代码。模型的探索效率、任务理解及总结可靠性也出现负向信号，但它们与错误反馈、资源限制相互混杂，不能独立归因。

原始结论“本次没有建立 RSI”仍然成立。需要修正的是原因解释：它不是一次已经排除适配缺陷的模型能力测量。23 项已有测试没有覆盖下面的元数据计量和改进摘要语义问题。

## 1. 上下文限制包含重复推理元数据

[broker.py](../src/mini_swe_rsi/broker.py) 在请求发往后端前检查 `len(json.dumps(messages, ensure_ascii=False)) > 60000`。这是宿主的序列化字符合同，不是模型服务报告的最大 token 窗口。

实际请求的 assistant 历史同时包含 `reasoning_content` 与 `provider_specific_fields.reasoning`，两者保存同一份推理文本，都会被字符检查计入。后端是否将这些辅助字段用于模型上下文，本次没有验证；无论如何，宿主预算已重复计算它们。

从最终轨迹移除本地 `extra` 与空字段后，重建下一次请求；同一处理对前一次请求得到的结果与模型总账中的真实请求完全相同，五份提案均校准通过。

| 提案 | 实际已调用次数 | 重建的阻断请求字符数 | 只去掉 provider_specific_fields | 仅保留角色与正文 |
|---|---:|---:|---:|---:|
| 递归 G1 | 18 | 60002 | 54863 | 50426 |
| 递归 G2 | 21 | 60158 | 55005 | 50671 |
| 递归 G3 | 25 | 65585 | 59430 | 54250 |
| 固定 G1 | 17 | 65640 | 61326 | 57675 |
| 固定 G2 | 19 | 60118 | 52308 | 45239 |

只移除供应商字段副本，四份提案的下一次请求就低于原有字符限制；仅按角色与正文计算，五份都低于限制。这只证明截断与计量方式有关，**不证明继续运行会产生修改或有效 RSI**。不能直接把全部推理字段删除作为通用修复，必须先确认当前后端的消息协议。

官方 mini 的观察模板已经把每条较长输出限制为头尾合计 10000 字符，不能说它完全没有截断。然而历史仍持续累积，单条完整读取 `default.py` 约 8043 字符，读取 `interactive.py` 原始约 10352 字符；这些探索连同多次目录检查，很快消耗当前字符合同。SICA 的专用探索工具被 bash 入口替代后，交互效率也需要单独验证。

## 2. 改进失败被摘要模块描述为成功

这是明确的状态传播缺陷：

1. [bridge.py](../runtime/bridge.py) 捕获 `agent.run()` 异常，写入失败 `result.json`，但正常返回，容器进程退出码仍为 0。
2. [sica.py](../src/mini_swe_rsi/sica.py) 虽记录了真实 `exit_status`，向原生 SICA 返回的 success 却只检查容器退出码。
3. [原生 runner.py](../vendor/sica/runner.py) 因此为改进摘要构造 `Agent code updated` 和成功分数 `1.0`。

五次真实摘要请求全部收到这种错误成功反馈，尽管五份源码差异均为空、终止原因均为上下文超限。独立评分与外层机制门槛没有因此被判成成功，所以最终停止结论未受伪成功评分替代；但供后续改进者读取的反馈已经被污染。

固定轨道 G1 的 [summary.txt](../runs/sica-qwen-20261011/results/run_2/agent_0/meta_improvement_logs/summary.txt) 进一步编造了“系统已最优、不需要修改”的解释。固定 G2 实际读取这份摘要，其后续记录也采纳了该解释。这条因果链同时暴露了错误状态反馈和模型不能可靠纠正错误摘要的问题，不能仅归咎于其中一方。

## 3. 排障资产混入改进证据

递归 G1 读取了 `results.pre_patch_fix.jsonl`，随后把评分资产修复前后的差异理解为 agent 代码改进。该文件实际保留的是补丁收集故障修复前的评分审计，不是候选策略变化。原始审计资产应该保留，但改进者的搜索视图需要明确当前有效证据，避免把排障结果作为策略收益来源。

早期补丁基准错误确实属于实现问题，已重建原补丁并重新评分。它影响了任务评分；五份提案没有任何写入命令，则不能直接解释成补丁评分器阻止了写代码。

## 4. 能判断哪些模型问题

- 五份提案共 100 次真实模型响应均为 `finish_reason=stop`，单次 completion 最大 378 tokens。当前提案失败不是输出达到 2048 tokens 后被截断，也不是改进提案的动作格式反复出错。
- 全部已执行命令均为目录浏览、文件读取或搜索，没有写入尝试。说明当前组合的探索收敛效率很低；尚未测到模型实际实现一个改进的能力。
- 在明确给出的目录结构下仍出现多次路径误读；错误摘要被接受，并被扩展成“系统已最终完成”等无依据判断。这些是任务理解和证据判断不足的信号，但错误成功反馈加强了混淆。
- H0 的开发集成绩为 6/30，说明当前模型与 Harness 组合存在解题限制；124/150 个完成尝试标记上下文超限，不能把这个成绩等同于模型不受限制时的编码能力。相同源码的重复运行分数差也不是 Harness 改进收益。

因此，不具备给“代码问题占多少、模型能力占多少”分配百分比的证据，更不能据此断言 4B 模型不能自改进。

## 5. 最小归因验证

先做工程修复，保持原失败运行封存：按真实 agent 终止状态传播失败；摘要明确记录“失败/未修改/修改待评测”，不能用进程退出码代表改进成功；规范文本消息的协议字段与计量，记录后端配置；给改进者提供当前有效开发证据，隔离排障副本。

这些边界修复应新增针对性验证：异常退出不会生成成功反馈、无修改不会被总结为代码已更新、重复元数据不会意外消耗语义上下文预算。只检查容器能启动与模型能调用不够。

随后用同一个 Qwen、相同起点和开发证据做少量独立诊断提案，先只改变适配边界，保持 30 次调用、600 秒等上限。若需要改变上下文合同，须使用单独标记的实验，记录相应 token 成本，不能与原实验混成同预算结果。先看是否形成可执行补丁，再做开发集独立评分；在此之前不重跑完整搜索或开启 val/test。

如边界修复后仍无法收敛，可追加明确限定一个可修改模块的诊断任务，区分“基础编辑能力”与“开放式发现改进的能力”。这种人工限定任务属于能力诊断，不能作为原生 RSI 成功证据。即使能够写出补丁，也仍需收益与递归继承评测，才能继续精简。

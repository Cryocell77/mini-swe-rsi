# mini-swe-rsi 在线自进化修改方案

状态：设计方案，尚未实施；不启动或恢复真实实验。

## 1. 目标与范围

实现如下闭环：当前 agent 完成一道开发任务，查看自己的执行反馈，在原 SICA 七步结构中诊断自身 Harness；没有可执行改进机会就继续下一题，有机会则提出、实现、检验修改；验收后的版本完成下一题，并承担后续诊断和改进。

新增独立 online 模式，保留 native 批量实验模式。复用官方 mini、固定上游七步定义、原角色/委员会、模型代理、任务环境和独立评分器。不训练模型，不引入更强改进模型，不在本轮同时精简框架或人工增加解题策略。所有模型调用统一使用启动时从 .env 冻结的模型与参数。

online 是明确的调度和验收扩展，不宣称原 SICA 已实现同样的逐题循环。保持 vendor 原文及 upstream.lock.json 不变，新增行为放在适配层，并记录差异。

本次是方案整理：不恢复已结束进程、不重测基线、不进行真实推理、不提交实现 commit。

## 2. 当前实现与需要改变的地方

1. Experiment.evolve 在候选生成后运行完整开发集，并依赖整批成绩进行后续选择；online 需要逐题任务游标。
2. 原 runner 分别选择父版本和最优改进者；online 固定本轮任务执行者、改进者、候选父版本为同一活动版本。
3. 七步成功完成第二步后直接推进第三步，Workflow.finish 仅认识 completed/failed；需要新增正常跳过状态，避免最后提交把它覆盖为 incomplete。
4. Driver.task 已保留轨迹、补丁和独立评分结果，可复用；需要建立面向诊断的公开反馈包及版本关联。
5. bridge 中委派角色复用启动时导入的 agent 类；不能用普通委派证明修改后的候选能运行。需要独立进程加载候选的检查入口。
6. ArchiveAnalyzer 和完整覆盖校验面向相同题集；online 不得用不同版本在不同题目上的平均分选优，不能删除 native 的完整覆盖校验来绕过问题。
7. 当前工作流不支持退出进程后从持久化对话恢复；online 首版支持阶段边界恢复，不能把启动新会话称为原会话续跑。

## 3. 身份、编号与继承

- H_v：已验收的活动 Harness 版本，v 只在接任成功时增加。
- T_i：预先冻结顺序中的第 i 个任务，任务游标与版本号独立。
- R_i：任务后的诊断/改进轮次，即使跳过也有记录。
- P_j：进入实现阶段的候选编号；候选可以失败，不占用活动版本号。

本轮任务执行者 = 本轮改进者 = 候选父版本 = H_v。禁止在线模式隐式回退到 H0 或历史最高分改进者。所有委派角色也加载 H_v 对应的归档 agent/model 类。

若接任 P_j，生成 H_(v+1)，下一题和下一轮改进均加载 H_(v+1)。若跳过或拒绝，下一题仍加载 H_v。重启进程加载归档源码，不在原 Python 进程中热替换已导入模块。

七步、模型代理、评分与版本管理是固定控制面；minisweagent 包中的源码、实际生效配置和资源是允许演化的 Harness。桥接层会覆盖的角色模板、预算和模型配置须明确列出，不声称这些覆盖项随候选继承。递归能力结论只覆盖实际可演化且被执行的部分。

## 4. 完整执行流程

```text
读取活动版本 H_v 和下一个任务 T_i
  -> H_v 执行 T_i，冻结第一次任务结果
  -> 独立评分，保存公开反馈
  -> 用 H_v 启动本轮七步
       1. 识别失效机制
       2. 识别有效机制
       [诊断决策点]
         无可执行改进 -> 正常跳过 -> 保留 H_v -> T_(i+1)
         有可执行改进 -> 3. 提案与委员会评审
                          4. 实现候选 P_j
                          5. 实际检查候选
                          6. 更新描述
                          7. 更新历史
                       -> 宿主验收并原子提交接任决策
                          接受 -> H_(v+1) -> T_(i+1)
                          拒绝 -> H_v     -> T_(i+1)
```

每道正常完成的任务，包括模型任务失败和成功任务，均进入步骤 1、2。基础设施失败先按现有明确重试/恢复规则处理；评分未知不能记成模型失败或用于比较。无法恢复的基础设施故障暂停在对应阶段，保留已发生调用。

下一题在本轮决策落盘之前不启动。任务结果在诊断前冻结，后续候选重做该题不能覆盖第一次作答成绩。

## 5. 七步与步骤 2 后的决策

| 步骤 | 在线模式要求 | 产物 |
|---|---|---|
| 1 失效机制 | 优先检查刚完成的任务，结合已公开历史；区分任务仓库错误、Harness 缺陷、模型行为和基础设施故障 | 失效机制报告、轨迹引用、相关 Harness 位置 |
| 2 有效机制 | 找出已起作用的行为、应保留的机制及可能的改进空间 | 有效机制报告、证据引用 |
| 决策点 | 当前模型决定 improve 或 skip，宿主校验结构、阶段及证据路径 | diagnosis.json |
| 3 提案与评审 | 根据诊断形成具体方案，保留原委员会；在候选测试前确定验收条件 | 提案、评审、冻结的检查计划 |
| 4 实现 | 编码角色修改当前版本的工作副本，只形成可追溯候选 | 源码差异、候选身份 |
| 5 检查 | 本地检查 + 宿主启动候选独立进程 + 开发任务比较 | 检查快照、执行身份、父子结果 |
| 6 描述 | 写明实际改动和已完成检查，不提前宣布总体收益 | description.txt |
| 7 历史 | 更新历史证据，区分当前题修复与尚待验证的泛化收益 | agent_change_log.md |

### 5.1 正常跳过条件

- 没有发现失效机制，也没有可进一步改进的有效机制。
- 发现有效机制，但证据只支持保留现状。
- 存在异常观察，但当前证据不足以形成可执行的 Harness 改进机会；必须明确记录不确定性，不写成系统没有问题。

任一步识别出有证据支持的改进机会即可进入第三步，不要求失效和有效机制同时存在。对模型能力不足的判断也必须基于证据；不能要求每次都把失败改写成一个 Harness 缺陷。

反馈缺失、工具读取失败、角色异常退出或必要诊断没有执行，属于 diagnosis_failed，不是正常 skip。

### 5.2 决策接口与状态语义

新增仅 online 模式、仅主协调者可调用的诊断决策操作，例如 diagnosis_decision。

两步完成后进入 diagnosis_pending，尚不暴露步骤 3 的完成工具。只接受明确的结构化决策，未决策前不能完成步骤 3 或启动编码委派。步骤 1、2 期间只允许诊断所需委派和公开只读检查。

diagnosis.json 保存 task_id、round_id、executor/proposer/parent、两步报告引用、失效/有效机制、改进机会、decision、reason、evidence_refs。宿主验证实际角色返回成功、报告存在、引用属于本轮公开证据；它不代替模型判断语义是否正确。

- skip：status=skipped_no_actionable_improvement，completed_steps=2，active=null，skipped_steps=[3,4,5,6,7]。
- improve：开放原步骤 3，其余顺序与完成工具保留。
- 原 native 模式：第二步成功后仍直接进入第三步。

Workflow.finish 必须保留正常跳过状态；提前直接提交不能冒充完成诊断或合法跳过。正常 skip 作为成功结束的诊断轮次返回，不记为成功改进。

跳过时不注册候选、不增加版本号、不改 agent_change_log.md，也不调用委员会、编码或候选测评。诊断报告和跳过原因存于宿主轮次归档，供后续任务查看。适配若需要临时诊断工作副本，它不是候选或新版本，跳过时不把它归入谱系。

## 6. 任务反馈与公开归档

复用 task_execution.json、trajectory.json、patch.diff、metrics 和独立评分。宿主整理事实，当前模型负责原因诊断，不新增一个人工编写的策略生成器。

公开反馈包含：任务说明、执行版本与模型身份摘要、退出状态、轨迹、命令结果、补丁、是否通过、资源消耗、计量完整性、原始证据路径和摘要。可提供确定性事实统计，例如空补丁、格式失败次数、重复命令次数；这些不能直接标记为确定根因。

完整轨迹按需读取，初始消息只放本题身份、事实概览与索引，不把全部历史对白塞进每个角色。全部角色可定位本题证据；步骤 1、2 的归档探索者还可访问过去已经公开的任务和诊断。

不公开参考补丁、私有测试、评分器内部文件、凭据、未来任务执行结果或 val/test。官方评分仅公开任务通过与否及允许的执行状态；agent 自己运行的公开测试输出可以进入反馈。

online 归档独立保存 chronological history，不能直接把不同版本做过的不同任务放入原 ArchiveAnalyzer 后按平均分排名。需要保留的原归档分析只用于有共同任务的可比记录，或由在线概览明确展示题目集合与不可比性。

## 7. 第 5 步候选检查

### 7.1 专用宿主接口

增加 candidate_check 操作及受认证的 broker/relay 路由。候选路径、当前题号和允许的检查集合由宿主已登记身份解析，不接受任意宿主路径或任意评分任务。

步骤 5 的主协调者发起请求，宿主固定候选执行快照，在独立进程、全新任务环境中调用实际候选。普通委派仍加载本轮 H_v，不能代替候选端到端检查。

检查采用独立 job_id 与持久化状态；重复请求返回已有工作或结果，不重复推理。由独立工作线程串行执行任务推理，主改进角色等待，不同时产生模型请求；broker 继续处理检查进程的模型/工具请求，避免宿主等待改进容器和改进容器等待宿主造成死锁。所有调用统一当前模型并单独计量。

### 7.2 检查内容

1. 语法、导入、实际配置加载和与修改相关的工程测试。
2. 验证修改所涉及运行路径；只看文件差异或 AST 摘要不足以证明行为改变。
3. 在新的题目容器中让候选重做当前开发题，与 H_v 在本轮第一次作答的冻结结果比较。
4. 小规模烟测先不增加回归题；扩展实验可预先固定少量已公开历史题作回归检查，并对父子使用同一集合。

历史题的父结果只有源码摘要等于当前 H_v 且合同一致时才能复用，否则必须实际运行 H_v。不得拿祖先版本成绩冒充当前父版本成绩。当前题复用首次父结果属于单次配对诊断，不是重复运行的统计证明。

已看到反馈后重做当前题，只能证明修复信号，不能证明泛化。检查时不给候选注入父版本作答或隐藏答案，使用相同公开题目和运行合同。

检查计划在步骤 3 冻结；失败后修改候选必须产生新的快照/检查修订记录，保留先前失败和成本，禁止覆盖或只保留最好一次。小规模烟测默认一个候选检查快照，不自动重采样。

### 7.3 检查后源码一致性

区分 full_source_hash 与 execution_hash：前者覆盖归档全部文件，后者覆盖实际可执行 Harness，包括 Python、配置、模板、包资源及实际参与加载的声明文件，排除描述/日志/测试产物等非运行文件。

第 5 步固定 execution_hash；步骤 6、7 只更新文档。接任前再次核对 execution_hash，若变化则原检查失效，需要新快照检查，不允许用旧结果接任新代码。

只改日志、描述或未加载的文件，不能作为有效行为修改。测试文件变更也不能单独满足 Harness 改进条件。

## 8. 验收与版本接任

本轮诊断与候选修改均由 H_v 完成。宿主执行预先冻结的验收规则，不自动设计策略。

接任前必须满足：

1. 七步完成且正常提交。
2. 候选存在实际运行 Harness 修改；相关代码/配置有加载及执行证据。
3. 语法、导入、所需工程检查通过。
4. 候选在所有已执行共同任务上的成功结果不低于父版本，不存在已观察成功题回退。
5. 有至少一个事先声明并通过的改进判据：当前题由失败变成功，或针对已诊断机制的同一检查在父版本失败、候选通过；不能只凭模型自评或源码发生变化接任。
6. 最终 execution_hash 等于通过检查的快照。

机制检查的父子测试内容必须一致并固定；若测试由模型提出，应保留完整测试内容与双方运行证据。这仍是有限验收，不证明没有未测回退。

通过后标记为 accepted_for_online_use，接任下一题；performance_benefit 仍记为未充分建立。候选检查失败、无运行修改、缺少收益证据或七步未完成，则保留 H_v，记录拒绝原因。正常 skip 与候选拒绝分别统计。

第一版不将 token/耗时的小幅下降作为默认接任依据，避免单次噪声带来晋升；需要效率判据时单独预先定义并冻结测量方法。本方案没有要求每轮必须产出新版本。

## 9. 持久化、恢复与资源合同

### 9.1 状态与布局

```text
runs/<online-run>/
  configuration.json             # online 合同、顺序、模型/服务、评分/镜像、检查策略
  online_state.json              # 活动版本、下一题、当前轮状态
  versions/H0000/agent_code/
  versions/H0001/agent_code/
  tasks/0001-<task_id>/            # 第一次任务结果及公开反馈
  rounds/R0001/                  # 两步诊断、决策、七步轨迹、公开检查索引
  proposals/P0001/               # 候选、差异和检查快照
  decisions/R0001.json           # 跳过/接受/拒绝及摘要
  events.jsonl
  private/                      # 私有评分、完整敏感运行数据
```

状态至少包括 task_running、task_done、feedback_ready、diagnosing、diagnosis_pending、skipped、improving、checking、decision_ready、round_committed、interrupted。工作流终态与宿主轮次状态分开保存。

### 9.2 恢复规则

- 保留现有单运行锁，并给任务、提案、检查和接任决策固定 ID。
- 已有任务执行结果但未评分，只恢复评分，不重新调用模型解题。
- 已完成两步并合法跳过，恢复后直接推进下一题。
- 已完成检查，复用同一快照和检查结果。
- 决策文件先原子落盘；再更新活动版本和游标。恢复按不可变决策重建状态，避免重复接任或漏推进。
- 模型、服务、源码或协议身份变化时拒绝混合恢复；必须创建新的实验。
- 诊断/七步对话在中间退出时记录 interrupted，保留源码和轨迹，不静默新建对话或假装续跑。首版实现阶段边界恢复；若要重启中断提案，必须显式指定并新建尝试记录。

不依赖 Docker 暂停内存作为持久恢复保证，不声称关机后能恢复同一模型会话。

### 9.3 资源与成本

沿用用户最新确定的现有原生/服务约束，启动时据当前 policy_contract 冻结；不新增 24 小时、30 分钟、共享调用数或价格总额硬上限。保留现有 SICA 角色迭代、单题 600 秒、工具限制、服务上下文和输出能力及适用计费合同，不重新引入旧 2048/32768 限制。

任务、诊断、评审、实现、检查、总结调用完整分别计量，汇总包括跳过和失败。模型推理并发保持 1。正常 skip 仍有两步诊断成本，不能记为零成本。

## 11. 实施、审查与测试顺序

### A. 状态与正常跳过

先实现独立 online 状态、轮次编号及第二步后决策。模拟验证两步后 skip、improve、诊断失败、提前提交和非法阶段调用；确认 native 七步顺序与原工具别名仍成立。

### B. 反馈与真实继承

接入逐题执行、公开反馈、同一活动版本诊断/改进和源摘要核验。模拟两轮不同运行行为的版本，证明下一任务和下一改进者实际加载新代码，而不是只更新版本标签。

### C. 候选检查与接任

接入宿主候选检查、快照、父子比较、检查计量和原子接任。验证加载修改后的代码；步骤 6/7 后执行摘要一致；候选拒绝保留父版本；检查回调不会死锁或重复调用。

### D. 原 SICA 对照与工程验收

核验固定 vendor 与原始锁摘要；逐项记录仅 online 生效的调度、跳过、检查和接任差异。运行相关现有回归和完整必要工程套件。native 的父/改进者选择、七步定义、完成工具、角色权限、模型身份、评分恢复和完整覆盖保护不得意外改变。

按用户最新要求，独立审查、工程测试和真实烟测验收后再提交本地实现 commit；不自动推送。真实运行先保存基准 commit、未提交改动状态、实际源码摘要与安全源码快照，测试结束后关联最终实现 commit。

冻结合同包含适配文件摘要，修改 bridge/workflow 后不能承诺历史实验可直接由新代码恢复；历史产物保持封存，需要旧代码时使用其冻结实现快照，禁止静默迁移旧合同。

### E. 三题真实闭环烟测

工程验收后，用独立 online 运行目录，从官方 H0 和当前 .env 开始，冻结开发集顺序前三题；不重跑整批基线，H0 对第一题的实际作答就是该题父结果。不启动固定轨道、探针、val/test 或代码精简。

期望路径为 H0 做 T1 -> H1 做 T2 并执行第二次改进 -> H2 做 T3，但不以必然出现两次修改作为程序保证。允许全部跳过或候选被拒绝；报告模型实际行为，不自动追加题目/重采样追求成功。

若三题范围内发生两次接任，必须核验两代行为改变、归档源码、进程加载和演化后改进者执行；否则只报告已实际验证的部分。每题之后都执行诊断及相应分支，第三题本轮结束后停止，不自动启动第四题。最后一轮生成但未执行后续任务的版本不能计为已证明任务继承。

用户此前选择的 20 题可作为后续在线开发范围，但不自动沿用旧失败题筛选。在线任务序列固定，不根据 H0 成败筛选下一题。旧实验资产只复用数据、镜像和评分程序；默认不把旧全量结果导入新在线改进上下文。

本次三题属于开发/机制检查。已在旧实验使用过的题目不能称为模型从未接触的题；若研究盲测收益，应另行确定未进入改进上下文的评估集合。

## 12. 验收矩阵

| 场景 | 必须结果 |
|---|---|
| 两步无机会 | 正常 skip，2/7，不调用评审/编码/检查，版本不变，下一题执行 |
| 只有有效机制且无需改动 | 正常 skip，保留有效机制证据 |

| 仅改文档 | 不满足运行 Harness 修改条件 |

## 13. 报告与交付

分别报告：循环执行是否成立、诊断跳过是否正确、候选是否产生实际 Harness 修改、修改是否被新进程执行、演化版本是否承担后续改进、已观察任务收益与检查局限。

在线成绩只使用每道任务在诊断前的第一次作答，不纳入候选重做的成绩。单独列出任务成绩、候选修复结果、跳过率、接任/拒绝数、基础设施失败、各阶段 token/耗时/已知费用，以及每次接任对应的判据。

需要量化收益时，在固定任务顺序上增加 H0 静态对照：对照不接触在线反馈，每题与在线链对应比较；整条在线实验及静态对照的总成本均报告。单条链上不同任务的分数走势不能直接解释为能力上升；长期 RSI 或改进能力收益还需要独立重复和专门对照。

交付代码、配置合同、上游差异说明、测试证据、在线谱系与报告。先完成机制验收，再决定扩展测评；不把未测的泛化、长期收益或无回退写成结论。
